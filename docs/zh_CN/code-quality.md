# 代码质量审计与 API 设计说明

本页记录截至 2.10.6 的代码审计结论，方便维护者理解现有结构、API 选择及后续重构优先级。

## 本次已经改进

### 不再要求附属插件依赖内部组队类

开局邀请组队原来只存在于 `bedwars-plugin` 的 `PreGameSquadManager`，附属插件无法在只依赖 API 模块时调用。现在新增 `PreGameSquad` 服务，并通过 `BedWars#getPreGameSquadUtil()` 暴露。

返回的成员和可邀请玩家列表均为不可变快照，调用方不能破坏内部队伍状态。

### 提供安全的竞技场查询

旧方法可能返回 `null`，竞技场列表还是内部 `LinkedList`。为保持二进制兼容，旧方法没有删除；新代码可使用：

- `findArenaByPlayer`
- `findArenaByName`
- `findArenaByIdentifier`
- `getArenasSnapshot`

这样能减少空指针和附属插件误删内部竞技场的问题。

### 补全配置访问 API

`Configs` 新增等级、经济奖励和声音配置入口，附属插件无需引用实现模块的静态字段。

### 大厅状态成为明确 API

`applyLobbyState` 统一应用冒险模式、飞行、拾取和大厅物品。它与只刷新物品的旧方法分开，避免 API 名称和实际副作用不一致。

### 配置文档集中管理

所有中文配置说明集中在 `ChineseConfigDocumentation`，配置架构升级时统一写入旧文件。竞技场动态队伍在每次保存前重新补注释，避免新建队伍没有说明。

### 方块生命周期职责拆分

`BreakPlace` 原来同时负责建造权限、床破坏、爆炸保护和玩家放置方块索引维护。2.10.4 将索引的添加、删除、爆炸/燃烧/褪色清理、重力方块迁移和活塞保护提取到 `PlacedBlockListener`。这样权限逻辑与方块生命周期可以分别审查和测试，也避免继续扩大已经较长的监听器。

### 热路径与背包监听清理

- 建图会话由 `List<Player>` 改为 `Set<UUID>`，查询为平均 O(1)，并在退出时清理。
- 位置保护判断统一使用同世界平方距离，保护半径只读取一次，不再用宽泛异常捕获掩盖错误。
- 删除没有任何副作用的关闭背包全量扫描；受保护物品移动改为单一路径判断，并补全拖拽和副手交换。

### 开局策略与火球计算可独立测试

2.10.5 将固定的“两名玩家、两支非空队伍”要求集中到 `ArenaStartPolicy`，删除散落在等待、离开和组队流程中的 `minPlayers`/队伍状态复合条件。火球击退计算也提取为不修改输入向量的纯函数，避免事件循环中的顺序依赖，并允许直接做方向回归测试。

TAB 页首、页尾及玩家行沿用原仓库的状态化语言模板；Paper 1.21.11 生命周期清理、持久占位符和队伍名字颜色作为兼容修复单独保留。

## 仍然存在的技术债

### Arena 类职责过多

`Arena` 当前约 2777 行，同时管理注册表、玩家生命周期、游戏状态、世界、任务、聊天辅助和大厅返回。后续应逐步拆成注册表、玩家会话、状态机和世界服务，但一次性重写风险很高。

`DamageDeathMove` 当前约 805 行，死亡判定、旁观、重生、移动限制和伤害规则仍耦合在同一监听器中。下一批低风险重构应先提取无状态的死亡分类与重生位置决策，再迁移会产生 Bukkit 副作用的流程。

### 大量静态全局状态

配置、竞技场注册表、语言和部分缓存使用静态字段，增加测试隔离和热重载难度。项目已经明确禁止热重载；长期可改为由主插件持有的服务对象。

### 旧 Bukkit API

聊天仍基于 `AsyncPlayerChatEvent`，属于兼容旧实现。未来可迁移到 Paper Adventure 的异步聊天事件，并以 `Component` 构建消息，减少颜色字符串拼接。

### 配置路径依赖字符串

竞技场、商店和升级中仍有不少动态字符串路径。可逐步增加类型化配置记录与校验报告，但必须保持现有 YAML 兼容。

### 部分异常被忽略

商店默认物品和配置解析中仍存在宽泛 `catch (Exception ignored)`。后续应改为带配置路径的限频警告，既保留容错，也让管理员能定位错误。

## 推荐的下一批 API

以下内容值得后续增加，但本次没有贸然暴露内部实现：

1. 类型化的死亡上下文 API：区分普通、虚空、最终死亡和有效攻击者。
2. 安全出生点解析服务：允许附属插件复用趴下/邻近安全点算法。
3. 地图生命周期服务：以只读状态报告备份、卸载、恢复和启用进度。
4. 类型化配置校验结果：返回错误路径、严重级别和修复建议。
5. 大厅保护扩展点：让附属插件登记允许交互的自定义物品或 GUI。

新增 API 时应遵循：优先不可变快照、明确可空性、避免暴露实现类、保持主线程约束文档、保留旧接口至少一个兼容周期。

代码安全边界、已修复漏洞和部署建议另见[安全审计与部署加固](security-audit.md)。
